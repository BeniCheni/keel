## Goal

keel can read a terms file for a worst-of autocall, reject anything malformed with a line-numbered error, and say exactly which payoff terms are verified. Nothing is ever filled in silently.

## The file format

The first line is `schema: mln-terms/0.1`. YAML 1.2 core schema, so dates are strings. No floats appear anywhere: money is integer cents, ratios are integer basis points (`9500` is 95.00%), and underlying price levels are decimal strings.

### Terms

Every field marked "term" below is a value plus where it came from, in one of three shapes.

```yaml
level: { value: 9500, status: advisor, source: advisor-email }
```

| Status | Meaning | `value` | Required companions | Forbidden |
| --- | --- | --- | --- | --- |
| `primary` | Pricing supplement or final terms | per field | `source`, whose kind is `primary` | `rule`, `note` |
| `document` | Confirmation or statement; authoritative only for what it states | per field | `source`, whose kind is `document` | `rule`, `note` |
| `advisor` | Screenshot or email from an adviser | per field | `source`, whose kind is `advisor` | `rule`, `note` |
| `user` | Typed by the user, no source | per field | none | `source`, `rule`, `note` |
| `estimate` | Generated by a named rule | per field | `rule` (string, 1 to 200 characters) | `source`, `note` |
| `assumed` | An explicit default | per field | `note` (string, 1 to 200 characters) | `source`, `rule` |
| `unknown` | Not known | `null` | none | `source`, `rule`, `note` |

A term in conflict has this shape instead. It needs at least two candidates, kept in file order. Each candidate is a full term with status `primary`, `document`, `advisor` or `user`, and follows that status's row above. Nothing picks a winner, even between two `primary` candidates.

```yaml
maturity:
  status: conflict
  candidates:
    - { value: 2031-06-16, status: document, source: confirm-a }
    - { value: 2031-06-17, status: advisor, source: email-b }
```

### Sources

`sources` maps a source ID (`^[a-z0-9][a-z0-9-]{0,63}$`) to `{ kind, file }`. `kind` is `primary`, `document` or `advisor`. `file` is a path relative to the user's data folder in one portable grammar: segments of `[A-Za-z0-9._-]+` joined by `/`, no segment equal to `.` or `..`, at most 255 characters. That grammar rejects rooted paths, drive letters, UNC paths and backslashes before any normalization. Whether a file resolves inside the folder (symlinks included) is checked later at the I/O boundary, not here.

Every `source` on a term or candidate must name an ID in `sources`, and that source's `kind` must equal the term's status.

### Field contract

Unknown keys are errors at every level. Plain fields are not terms.

| Path | Required | Shape | Value |
| --- | --- | --- | --- |

| `category` | yes | plain | `mln` |

### Schema versus loader

The JSON Schema (`schemas/mln-terms/0.1.json`, draft 2020-12) enforces structure, required fields, types, enums, ranges, patterns (including the path grammar and source IDs), unknown keys, and the per-status companions as discriminated definitions. The loader runs the schema and maps each schema failure to an error code (a path-grammar failure is `source-path`, a range failure `out-of-range`, and so on). The loader alone enforces what JSON Schema cannot see: YAML lexical rules (line 1, duplicate keys, anchors and aliases, positions), that each `source` exists and its kind matches the status, real Gregorian dates, schedule order, and the CUSIP check-digit warning.

## Scope

1. **Schema** as above.
2. **Loader.** `loadTerms(text: string, fileName: string)` in `packages/core/src/terms/`. Pure: it takes text and never reads files. It returns either `{ ok: true, terms, warnings, dateFlags }` or `{ ok: false, errors }`.
   - `terms` holds only values that came from the file. Absent optional fields stay absent; nothing is defaulted.
   - `warnings` and `errors` are diagnostics `{ code, path, line, column, message }`, in document order. `message` is a sentence a person can act on.
   - `dateFlags` maps a term path to its flags.
   - Error codes: `yaml-syntax`, `schema-line`, `duplicate-key`, `alias`, `unknown-key`, `missing-required`, `wrong-type`, `out-of-range`, `invalid-date`, `unknown-status`, `status-fields`, `conflict-candidates`, `source-missing`, `source-kind`, `source-path`, `schedule-order`. Warning code: `cusip-check-digit`.
3. **Paths** in diagnostics, flags and the summary are written as dotted keys with zero-based list indices, for example `underlyings.members[2].initial`.
4. **Verification summary.** `verificationSummary(terms)` returns `{ verified, total, unverified }`. Every payoff term is critical, so there is one list. The payoff paths, in this fixed order:
   1. `dates.maturity`
   2. `dates.first_call_observation`
   3. `dates.observation_schedule`, counted as one path. It is verified only if present, nonempty, and every entry is `primary`. Absent counts as unverified.
   4. `underlyings.members[i].initial`, one path per member, in member order
   5. `underlyings.performance_rounding`
   6. `call.level`, `call.non_call_months`, `call.frequency`
   7. `premium.rate_per_year`, `premium.accrual`
   8. `barrier.level`, `barrier.observation`, `barrier.below_barrier`

   A path is verified only when its status is `primary`. `total` is the number of paths; `unverified` lists the unverified paths in the order above.
5. **Date flags.** `dateFlags(isoDate)` returns `['weekend']` for a Saturday or Sunday and `[]` otherwise, computed from the ISO date alone (no clock, no time zone). The loader flags every known date value, conflict candidates included. It never rejects a weekend date.
6. **Fixture generator.** `tools/generators/terms/`, registered in `fixtures:regen` as `terms` version 1 with a fixed seed. It owns `fixtures/synthetic/terms/`. Fixtures are never hand-typed.
   - `valid/example-autocall.yaml`: a fictional "Example Bank SA" note on tickers ALFA, BRVO, CHRL and DLTA. Its statuses are fixed by this spec (below); the seed chooses the values only.
   - `valid/minimal.yaml`: only required fields, four members, every term `primary`.
   - `invalid/`: each file applies exactly one mutation to `minimal.yaml`, so it violates exactly one rule. At least one file per error code except `yaml-syntax`, and one file per variant where a code has several: `unknown-key` for a nested key (`call.levle`) and a top-level key; `status-fields` for `unknown` with a non-null value and for `estimate` without `rule`; `source-kind` for `primary` citing an `advisor`-kind source; `invalid-date` for `2027-02-30`; and `source-path` for each of `..`, a leading `/`, `C:/`, `//server/share` and a backslash.
   - Fixture CUSIPs pass the check digit and start with `ZZZ`. `tools/tripwire/allowlist.txt` lists each exactly, with glob `fixtures/synthetic/terms/**` and reason "synthetic fixture".

## Honesty tests (`terms.honesty.test.ts`)

- A `document`, `advisor`, `user`, `estimate`, `assumed` or `unknown` status never counts as verified, for any payoff path.
- A conflict never counts as verified, even between two `primary` candidates, and keeps every candidate in file order.
- A `primary` status backed by a source of another kind is an error, never a verified term.
- The loader never invents a value: every leaf in `terms` exists in the input, and absent optional fields stay absent. Warnings and date flags live outside `terms`.
- `unknown` stays `null` all the way through.
- An absent observation schedule counts as unverified, never drops out of `total`.

## Non-goals

The payoff engine; schedule generation and the holiday calendar; file I/O and symlink containment; PDF import; any UI; writing or editing terms files; resolving conflicts (a later slice; a document resolving a conflict still does not verify a payoff term unless it is the `primary` source).

## Acceptance criteria

All terms tests run with `pnpm --filter @keel/core test terms`. Each criterion names the test file that carries it.

| # | Criterion | Test file and what it asserts |
| --- | --- | --- |
| AC1 | Every valid fixture loads with no errors | `terms.valid.test.ts`: the discovered valid-fixture count equals the generator's manifest count and is at least 2; each loads with `ok: true` and zero errors |
| AC2 | Every invalid fixture fails with exactly its intended error | `terms.invalid.test.ts`: a table from the generator manifest giving, per file, the one expected code, path, line and column; asserts exactly one error and that it matches |
| AC3 | The summary matches the frozen values | `terms.summary.test.ts`: deep-equals the two JSON objects in this spec |
| AC4 | Honesty tests pass, and each fails when its guarded behaviour is broken | `terms.honesty.test.ts` under `pnpm verify`; the PR body names, per mutant, the test that kills it |
| AC5 | `dateFlags` marks Saturdays and Sundays and nothing else | `terms.dates.test.ts`: 14 consecutive dates spanning two weekends, a leap day, and the invalid date `2027-02-30` rejected by the loader |
| AC6 | The schema and the loader each enforce their half | `terms.schema.test.ts`: validates JSON directly against `schemas/mln-terms/0.1.json` for nested unknown keys, status companions and the path grammar; separately runs the loader on each `source-path` and referential fixture |
| AC7 | `pnpm verify` stays green, including tripwire, network and determinism | `pnpm verify` |

## Mutation floor

At least three killed mutants per claim, listed in the PR body with the killing test. Required among them: counting `document` as verified; dropping the second conflict candidate; accepting an alias; treating Friday as a weekend; filling a missing `estimated_value` with 0; accepting a `primary` term backed by an `advisor` source; accepting a `..` path segment; dropping an absent schedule from `total`.

## Dependencies

Candidates: a YAML 1.2 parser that reports positions and duplicate keys, and a JSON Schema 2020-12 validator. The builder may instead hand-write validation against the schema. Every dependency added needs a justification and license line in the PR body.
