## Goal

A terms file can state the note's final valuation date, with provenance, and keel counts that date among the payoff terms. Nothing infers it. Without this term, the last schedule entry is the only candidate. S02's estimate can leave out the slot that rolls past maturity, so a monthly note shows 54 entries where the research counts 55. Taking the last entry would then put the maturity test a month early.

## Decisions

Each of these is open to the plan challenge, except where a ruling of Beni's settles it.

1. **One optional term, `dates.final_valuation`.** It is an ISO date `YYYY-MM-DD` and a real Gregorian date, with the same term shapes as `dates.first_call_observation`. It is optional, and an absent term counts as unverified, as an absent observation schedule does.
2. **The term arrives in schema 0.2 (Beni's ruling of 2026-11-10, "Bump to 0.2").** The review skill requires the schema version to move when the shape changes. `schemas/mln-terms/0.2.json` is 0.1 with its `$id`, `title` and `schema` constant set to `mln-terms/0.2`, plus the optional term, and `0.1.json` does not change.
   - The loader reads both. Line 1 may be `schema: mln-terms/0.1` or `schema: mln-terms/0.2`, and the file is validated against the matching schema.
   - A 0.1 file cannot state the term: there it is `unknown-key`.
   - `Terms["schema"]` becomes `"mln-terms/0.1" | "mln-terms/0.2"`. The release that ships this is `v0.1.0`, a minor, which meets "A terms-schema bump is always at least a minor".
3. **The loader checks the date and nothing more.** It checks for a real Gregorian date and adds the weekend flag. It does not compare the date with maturity or the schedule, because those comparisons are payoff semantics, and S03 owns them.
4. **The schedule does not change.** `observationSchedule` still steps to maturity and does not read the new term. S03 decides how the final valuation date splits a schedule.
5. **The fixture change is the smallest that tests the term and the version.**
   - `example-autocall.yaml` moves to 0.2 and gains the term with status `primary`.
   - `minimal.yaml` stays 0.1, with required fields only.
   - Two new invalid fixtures: the term in a 0.1 file, and `invalid-date` on the term in a 0.2 file.
6. **This slice carries two items owed to the next slice that touches `packages/core`.** One is Medium 2.5-1 from PR #30's Pass 2.5. The other is idea 29, which Beni ruled rides the next slice that touches `packages/core`; S02 touched `packages/core` and did not carry it.

## Scope

### Schema and loader

- `schemas/mln-terms/0.2.json` is `0.1.json` with its `$id`, `title` and `schema` constant set to `mln-terms/0.2`, plus `dates.final_valuation`, defined as `dates.first_call_observation` is and not required.
- The loader picks the schema from line 1, using the same line-1 rule as today for either value. Any other value is `schema-line`, as now. A file that parses as YAML but whose line 1 is not a marker is still judged against a schema, so its other faults are reported: the one its parsed `schema` value names, or 0.1 when that value names neither. So a 0.2 file with a fault on line 1 is not also reported against 0.1.
- In a 0.2 file the loader accepts the term in every status shape, conflict included. It reports `invalid-date` at `dates.final_valuation.value` (or the candidate's `.value`) for a value that is not a real Gregorian date, and flags a weekend date in `dateFlags`, candidates included.
- `Terms["dates"]` gains `final_valuation?: Term<string>`. Absent stays absent. Nothing is defaulted.
- A 0.1 file and a 0.2 file with the same content, apart from line 1, load to `terms` that differ only in `schema`.

### Verification summary

`verificationSummary` adds `dates.final_valuation` as a payoff path, right after `dates.first_call_observation`, for files of either version. It is verified only when present with status `primary`, and an absent term counts as unverified, so a 0.1 file always lists it. `total` becomes 13 plus the number of members.

### Date flags

The loader's `dateFlags` and S02's `termDateFlags` both add the key `dates.final_valuation`, or `dates.final_valuation.candidates[i]` for a conflict, placed after `dates.first_call_observation`. They add it only when the term is present with a known value.

### Fixture generator

The generator moves to version 2 with the same seed. It changes `fixtures/synthetic/terms/` in the three ways below. The manifest changes with them: its `version` line moves from 1 to 2, and it gains the two new invalid entries. Every other byte stays unchanged:

- **`valid/example-autocall.yaml`.**
  - Line 1 becomes `schema: mln-terms/0.2`.
  - It gains `dates.final_valuation` with status `primary` and source `supplement`, as the last key of `dates`. Its value is five calendar days before the earlier maturity candidate. The generator derives that value and draws nothing from the seed for it, so every other value keeps its bytes.
- **`invalid/final-valuation-in-0.1.yaml`.** `minimal.yaml` with `dates.final_valuation: { value: 2027-03-01, status: primary, source: supplement }` added. Its one expected error is `unknown-key` at `dates.final_valuation`.
- **`invalid/invalid-date-final-valuation.yaml`.** `minimal.yaml` moved to 0.2 by its line 1, with `dates.final_valuation: { value: 2027-02-30, status: primary, source: supplement }` added. Its one expected error is `invalid-date` at `dates.final_valuation.value`. S01 has every invalid file apply one mutation to `minimal.yaml`. For a 0.2-only rule, this spec applies that mutation to `minimal.yaml` moved to 0.2, and the generator's comment on that mutation says so.

Both new manifest entries give the path, line and column, and AC1 asserts all three.

### Purity test (Medium 2.5-1)

The fix is two changes:

- `packages/core/src/schedule/test-support/nested/depth-marker.ts` is a new pure file, two folders below `schedule/`, that exports one constant. No product file imports it.
- `packages/core/src/schedule/schedule.purity.test.ts` also lists `packages/core/src/schedule/` recursively with `node:fs`, and requires the glob's keys to equal the non-test `.ts` files in that listing.

With the marker in place, a glob that does not recurse misses a file the listing holds, so the comparison fails.

### Loader ordering tests (idea 29)

Two tests in `packages/core/src/terms/terms.invalid.test.ts` pin behaviour the loader already has:

- A file with an integer token fault, such as `level: { value: 09500, ... }`, and an unknown key elsewhere reports both diagnostics.
- Two faults whose path order reverses their line order come out in line order.

## Frozen values

`verificationSummary` on `minimal.yaml` (0.1) returns exactly:

```json
{ "verified": 15, "total": 17, "unverified": ["dates.final_valuation", "dates.observation_schedule"] }
```

On `example-autocall.yaml` (0.2):

```json
{
  "verified": 8,
  "total": 17,
  "unverified": [
    "dates.maturity",
    "dates.observation_schedule",
    "underlyings.members[2].initial",
    "underlyings.members[3].initial",
    "underlyings.performance_rounding",
    "call.level",
    "premium.rate_per_year",
    "premium.accrual",
    "barrier.level"
  ]
}
```

`example-autocall.yaml`'s new term has value `2031-07-09`, a Wednesday and not an NYSE closure. `termDateFlags` on that file returns the object S02 froze plus `"dates.final_valuation": []`. The loader's `dateFlags` gains the same key and value.

These values replace S01's two frozen summaries and S02's frozen `termDateFlags` object once this slice's build merges. The PM updates those two specs to match in the next docs PR after that merge.

## Honesty tests

Extend `terms.honesty.test.ts`:

- `dates.final_valuation` is never verified when it is absent, when it is a conflict (even between two `primary` candidates), or when its status is `document`, `advisor`, `user`, `estimate`, `assumed` or `unknown`.
- An absent term stays absent in `terms` and stays in `total`, in a 0.1 file and in a 0.2 file.
- A 0.1 file never yields a `final_valuation` key in `terms`.

## Non-goals

- Comparing the final valuation date with trade, maturity, the first call observation or the schedule. S03 does that.
- Estimating the date, or generating it from a rule.
- Any change to `observationSchedule` or `scheduleDiff`.
- Removing schema 0.1, or migrating files from 0.1 to 0.2.
- Payment dates.
- The payoff engine.
- Any UI.
- The three PR #30 items that `docs/v0.1.0-ideas.md` records as ideas 51 to 53.
