# S02.1: Final valuation date term

- Status: drafted 2026-11-10 by the PM (Claude), on Beni's ruling of 2026-11-10 ("Schema term first (Recommended)") that S03 reads the final valuation date from a term rather than from the last schedule entry. No code exists yet.
- Release: non-release follow-up slice toward `v0.1.0`. Starts only after this spec merges. S03's build starts only after this slice's build merges.
- Builder: Cursor, Grok 4.7 Extra High (sensitive-path slice), in one draft PR on branch `s02.1/final-valuation`.
- Sensitive paths the build touches: `schemas/**`, `packages/core/**`. It also regenerates `fixtures/synthetic/terms/`. This spec PR touches none.
- Design rung: none (no UI).
- Stories served: 3.1 provenance on every term, 3.5 date sanity. S03 reads the term for 4.1 and 4.3.

## Goal

A terms file can state the note's final valuation date, with provenance, and keel counts that date among the payoff terms. Nothing infers it. Without this term, the last schedule entry is the only candidate. S02's estimate can leave out the slot that rolls past maturity, so a monthly note shows 54 entries where the research counts 55. Taking the last entry would then put the maturity test a month early.

## Decisions

Each of these is open to the plan challenge.

1. **One optional term, `dates.final_valuation`.** It is an ISO date `YYYY-MM-DD` and a real Gregorian date, with the same term shapes as `dates.first_call_observation`. It is optional so that existing files stay valid. An absent term counts as unverified, as an absent observation schedule does.
2. **Schema 0.1 is amended in place, with no version bump.** No release has shipped the schema, and every file valid today stays valid. A file that uses the new term fails a loader from before this slice, and no such loader has shipped.
3. **The loader checks the date and nothing more.** It checks for a real Gregorian date and adds the weekend flag. It does not compare the date with maturity or the schedule, because those comparisons are payoff semantics, and S03 owns them.
4. **The schedule does not change.** `observationSchedule` still steps to maturity and does not read the new term. S03 decides how the final valuation date splits a schedule.
5. **The fixture change is the smallest that tests the term.** `example-autocall.yaml` gains the term with status `primary`. `minimal.yaml` holds required fields only, so it stays unchanged. One new invalid fixture applies `invalid-date` to the new path.
6. **This slice carries two items owed to the next slice that touches `packages/core`.** One is Medium 2.5-1 from PR #30's Pass 2.5. The other is idea 29, which Beni ruled rides the next slice that touches `packages/core`; S02 touched `packages/core` and did not carry it.

## Scope

### Schema and loader

- `schemas/mln-terms/0.1.json` gains `dates.final_valuation`, defined as `dates.first_call_observation` is, and not required.
- The loader accepts the term in every status shape, conflict included. It reports `invalid-date` for a value that is not a real Gregorian date, and flags a weekend date in `dateFlags`, candidates included.
- `Terms["dates"]` gains `final_valuation?: Term<string>`. Absent stays absent. Nothing is defaulted.

### Verification summary

`verificationSummary` adds `dates.final_valuation` as a payoff path, right after `dates.first_call_observation`. It is verified only when present with status `primary`, and an absent term counts as unverified. `total` becomes 13 plus the number of members.

### Date flags

The loader's `dateFlags` and S02's `termDateFlags` both add the key `dates.final_valuation`, or `dates.final_valuation.candidates[i]` for a conflict, placed after `dates.first_call_observation`. They add it only when the term is present with a known value.

### Fixture generator

The generator moves to version 2 with the same seed. It changes `fixtures/synthetic/terms/` in two ways and leaves every other byte unchanged:

- `valid/example-autocall.yaml` gains `dates.final_valuation` with status `primary` and source `supplement`, as the last key of `dates`. Its value is five calendar days before the earlier maturity candidate. The generator derives that value and draws nothing from the seed for it, so every other value keeps its bytes.
- `invalid/invalid-date-final-valuation.yaml` is `minimal.yaml` with `dates.final_valuation: { value: 2027-02-30, status: primary, source: supplement }` added. Its one expected error, `invalid-date` at `dates.final_valuation`, is in the manifest with its line and column.

### Purity test (Medium 2.5-1)

`packages/core/src/schedule/schedule.purity.test.ts` also lists `packages/core/src/schedule/` recursively with `node:fs`. It requires the glob's keys to equal the non-test `.ts` files in that listing, so the control pins recursion and not one folder.

### Loader ordering tests (idea 29)

Two tests in `packages/core/src/terms/terms.invalid.test.ts` pin behaviour the loader already has:

- A file with an integer token fault, such as `level: { value: 09500, ... }`, and an unknown key elsewhere reports both diagnostics.
- Two faults whose path order reverses their line order come out in line order.

## Frozen values

`verificationSummary` on `minimal.yaml` returns exactly:

```json
{ "verified": 15, "total": 17, "unverified": ["dates.final_valuation", "dates.observation_schedule"] }
```

On `example-autocall.yaml`:

```json
{
  "verified": 8,
  "total": 17,
  "unverified": [
    "dates.maturity",
    "dates.observation_schedule",
    "underlyings.members[2].initial",
    "underlyings.members[3].initial",
    "underlyings.performance_rounding",
    "call.level",
    "premium.rate_per_year",
    "premium.accrual",
    "barrier.level"
  ]
}
```

`example-autocall.yaml`'s new term has value `2031-07-09`, a Wednesday and not an NYSE closure. `termDateFlags` on that file returns the object S02 froze plus `"dates.final_valuation": []`. The loader's `dateFlags` gains the same key and value.

These values replace S01's two frozen summaries and S02's frozen `termDateFlags` object once this slice's build merges. The PM updates those two specs to match in the next docs PR after that merge.

## Honesty tests

Extend `terms.honesty.test.ts`:

- `dates.final_valuation` is never verified when it is absent, when it is a conflict (even between two `primary` candidates), or when its status is `document`, `advisor`, `user`, `estimate`, `assumed` or `unknown`.
- An absent term stays absent in `terms` and stays in `total`.

## Non-goals

Comparing the final valuation date with maturity, the first call observation or the schedule (S03). Estimating the date, or generating it from a rule. Any change to `observationSchedule` or `scheduleDiff`. A schema version bump. Payment dates. The payoff engine. Any UI. The three PR #30 items that `docs/v0.1.0-ideas.md` records as ideas 51 to 53.
