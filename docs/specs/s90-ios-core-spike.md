## Is story 9.1 enough as the phone's only data path?

The test comes first because every row below depends on it. The assumption is that the desktop app is the source of truth, and that its export reaches the phone through the Files app, with no network and no sync service.

**As transport, yes.** Story 9.1 produces plain YAML and CSV files. The phone picks them through the Files app and needs no account, server or network. AirDrop to Files and a USB copy through Finder keep the files between the owner's own devices. iCloud Drive also appears in Files, but a file put there leaves the owner's machines, so the phone's copy names that difference. Story 9.1 is not built yet, so the spike uses a synthetic stand-in generated by seed.

**As content, no.** Story 9.1's story sentence names terms, observations and alerts. Its acceptance says a round-trip import reproduces the same state and does not list them, so this spec reads "the same state" as the state of that export. The Section 8 floor for the phone, "a read-only responsive view of Today and the instrument summary", needs more:

### Alerts: what can be scheduled ahead

iOS gives the app no timed background run it can rely on (`BGTaskScheduler`'s `earliestBeginDate` sets a time before which a task will not run, and not a time it does), and on the phone a close arrives only by import. So a rule can reach a closed app only when its fire time is known at import. Severity keeps Section 4's meaning: High and Critical become a notification, Notice goes in a weekly digest notification, and Info stays in the app.

| Alert | In M1 as | Scheduled ahead? | On the phone |
| --- | --- | --- | --- |
| A1 Barrier proximity | Must | No | After import only |
| A2 Likely call | Could | No | After import only |
| A3 Observation approaching and result | Must | Reminders yes, result no | T-5 in the digest, T-1 as a notification, result after import |
| A4 Call detected | Must | No | After import. A scheduled prompt names the observation date in the imported terms and the applicable closes present in that snapshot |
| A5 Maturity approaching | Should | Yes | T-180, T-30, T-5 |
| A6 Rating or outlook change | Should | Age only | Rating-age timer, only if the export carries a rating date |
| A7 Large single-name move | Could | No | After import only |
| A8 Stale data | Must | Yes, as a timer | Last close plus 3 trading days, and one per observation date; each import resets them. The trading-day count needs the holiday calendar, which comes with the schedule slice |
| A9 Terms still unverified | Must | Yes | T-30, T-7, weekly digest line |
| A10 Source conflict | Must | No | Raised at import |
| A11 Corporate action | Could | No | After import only |
| A12 Review ritual | Not in the M1 list | Yes | Quarterly digest line |

Two limits that follow, for the ADR:

- A scheduled notification fires whatever has happened since. A note called on the desktop keeps its T-1 reminders on the phone until the next import cancels them. So each notification's first line says it comes from the imported snapshot and names the applicable data dates, or says that no observation date is present. Its title, subtitle and body describe only that snapshot and dates recorded in it. None claims a current desktop state: an observation still ahead, a note not called, a close missing on the desktop, terms still unverified, or a current rating. A9 says the terms were unverified in that snapshot; A8 names the closes that snapshot contains. An estimated date says it is estimated. The same wording covers a timer that fires early because the device clock moved.
- The newest observation `as_of_date` is labelled only as the latest observation present, not as the export time or the freshness of every holding. Screens and notifications name the applicable holding and series dates; a newer close for one series cannot freshen another. With no observations, they say no observation date is present. Terms and alerts keep their own dated provenance; an observation date cannot date them. The import screen separately shows when the phone imported the files. The phone never uses a file's modification time, which AirDrop or Finder can change.
- The pending limit: An Apple staff answer confirms a limit of 64 pending requests per app, without promising which requests survive an overflow ([thread](https://developer.apple.com/forums/thread/811171)). Apple's `UNUserNotificationCenter` page states no number, so Q5 records what the device keeps, and whether a repeating trigger counts as one. Months 6 to 60 are 55 observations, which alone fit under 64. But T-1 and A8's observation-date timer make two requests per observation, 110 before A5 and A9, so the app selects the soonest requests itself within that limit and refills its rolling window on each open and import. It does not rely on the system to choose them. If the phone is not opened before that window ends, no later reminder is promised.

### Q1 Bundle

Can `@keel/core`, including `ajv` 8.20.0 and `yaml` 2.9.1, build into one script with no Node built-ins and load into a JSContext from a Swift test target that runs on macOS?

```bash
pnpm --dir spike/ios-core --ignore-workspace install --frozen-lockfile && node spike/ios-core/build.mjs && node spike/ios-core/check-bundle.mjs
```

```bash
swift test --package-path spike/ios-core --filter BundleLoadTests
```

`check-bundle.mjs` exits nonzero on `require(`, a `node:` specifier, a reference to `process`, or the string `montecarlo`, and prints the bundle's bytes. `BundleLoadTests` fails on any JSContext exception and asserts that `dateFlags`, `loadTerms` and `verificationSummary` are functions.

Known traps, each run in Node with the real libraries, and none yet in a JSContext:

- `yaml`'s `exports` map gives Node its `process`-using build and everything else the browser build, so the bundle must not take the `node` condition.
- `ajv`'s `getLogger` returns the global `console` when no logger is given (`ajv/dist/core.js:545`), and `schema-map.ts` gives none. With the global absent (`delete globalThis.console`), `new Ajv` throws `ReferenceError` at module load, so the bundle does not load. With it set to `undefined`, `new Ajv` and `compile` complete. Those are two different hosts.
- `yaml`'s browser `warn` calls `console.warn` when `logLevel` is `warn` or `debug`, and a document's default is `warn`. `example-autocall.yaml` through `parseDocument` and `toJS` gives no warning and no throw. A complex key does warn. With no `console` that throws inside `toJS`, and the catch in `load.ts` would report it as `alias`.
- `fast-uri` calls `new URL` on one path. `check-bundle.mjs` does not look for `console`, `URL` or `new Function`, so `BundleLoadTests` reports which of those a JSContext defines.

Whether a JSContext defines `console` decides these. Any shim the host needs is a finding, listed in the results.

### Q2 Parity

For every file in `fixtures/synthetic/terms/`, valid and invalid, does the JSContext output match Node's byte for byte, including each diagnostic's line, column and order? There are 31 files, 2 valid and 29 invalid (`git ls-files fixtures/synthetic/terms | grep -c '\.yaml$'`).

```bash
sh spike/ios-core/run-parity.sh
```

```bash
sh spike/ios-core/run-parity.sh --inject-diff
```

The first exits 0 only if every comparison is byte-identical, and prints fixtures, locales, engines and variants. The second alters one byte of one output and must exit 1, or the harness cannot fail.

- **Node side:** runs `packages/core/src/index.ts` directly, unbundled, so that a bundling difference counts as a difference.
- **Output:** one line per file, `JSON.stringify({ file, result, summary })`, where `summary` is `verificationSummary(result.terms)` when `result.ok`.
- **Comparison:** `cmp`, in both engines, under `en_US` and `haw_US`, and for each bundle variant in Q3.
- **Locale check:** each run records `new Intl.Collator().resolvedOptions().locale`. If the two runs in one engine report the same locale, that engine's run fails: a test under one locale twice is not a test under two. Apple's JSContext API lists no locale setter, so the builder finds the route: launch arguments, or the Region setting in macOS or on the iPhone. If no second locale can be run in an engine, clause 1 fails.
- **On the iPhone:** the harness app runs the same fixtures under both locales for each variant and logs a SHA-256 of each output, and `run-parity.sh --compare-device <log>` compares them with Node's. A difference fails clause 1. This is Beni's run.

`load.ts` no longer sorts with `localeCompare`: Beni's ruling replaced it inside PR #13, at `c527df8`, after `dedupe` gave a different order under `LC_ALL=haw_US.UTF-8`. At `3bceb20`, `git grep -n localeCompare -- packages` prints only a test stub, and neither library's loaded code calls a locale API (`grep -rlE 'localeCompare|toLocale|Intl\.' node_modules/.pnpm/yaml@2.9.1/node_modules/yaml/browser/dist node_modules/.pnpm/ajv@8.20.0/node_modules/ajv/dist | wc -l` prints `0`). The two-locale test stays: it is the check that nothing else depends on locale.

**Reported, not gating:** the same comparison on inputs edited in memory, because earlier reviews found them to be edge cases. A complex key, an alias as a key, a leading BOM, CRLF line endings, a character outside the Basic Multilingual Plane before a fault (columns count UTF-16 units here), `0000-02-29`, flow nesting to 2000 and block nesting to 1000. A divergence is reported in the results and put to Beni. It does not by itself make a close call.

### Q3 Code generation and load time

`schema-map.ts` calls `ajv.compile` at load, and `ajv/dist/compile/index.js:89` is `new Function`. Does that work inside a JSContext? How long does it take without a JIT on a real iPhone? Does an `ajv` standalone precompiled validator remove the question?

Two bundle variants, each through Q2:

- **`compile`:** the merged core, unchanged.
- **`standalone`:** the spike's build swaps `schema-map.ts`'s compile for a generated validator through a build-time plugin. Core is not edited. If this is the variant that passes, the core change is filed through the normal workflow and is never made on the spike branch.

```bash
swift test --package-path spike/ios-core --filter LoadTimeTests
```

```bash
xcodebuild build -project spike/ios-core/App/KeelSpike.xcodeproj -scheme KeelSpike -configuration Release -destination "platform=iOS,id=$KEEL_SPIKE_UDID" -derivedDataPath spike/ios-core/.build/ios DEVELOPMENT_TEAM="$KEEL_SPIKE_TEAM" -allowProvisioningUpdates
```

```bash
xcrun devicectl device install app --device "$KEEL_SPIKE_UDID" spike/ios-core/.build/ios/Build/Products/Release-iphoneos/KeelSpike.app
```

```bash
xcrun devicectl device process launch --device "$KEEL_SPIKE_UDID" --console "$KEEL_SPIKE_BUNDLE_ID"
```

No Swift or Xcode command in this spec has been run, because this Mac has no full Xcode. These three device lines are the PM's reading of Apple's tools, not a confirmed Personal Team command sequence. The builder confirms or replaces them and records what ran, keeping what they are for: a Release build with `ENABLE_TESTABILITY` at its Release default, a newly launched process, and no debugger attached. A Debug run is not a substitute. Apple's archived Xcode 7 release notes warn that Enable Testability prevents optimizations that depend on not exporting internal symbols. That is narrower than disabling all optimization and is not a measurement of the current compiler.

**Gated, per variant:** five fresh launches of the harness app. In each, create a JSContext and evaluate the bundle, which includes `ajv.compile` for the `compile` variant, then make the first `loadTerms` call on `example-autocall.yaml`. Report the median of the five for each. Retain the paired measurements for each launch and evidence that it was a new process; reactivating an existing process does not count as a fresh launch. These timings start at JSContext creation, not at tapping the app icon.

**Reported, not gated:** the worst of those five, plus 20 more JSContexts and 20 more `loadTerms` calls in one process, each with its median and worst. The 20 share a process, so their median is a warm number. The results also say whether the device's run differs from a macOS JSContext, because "no JIT in-app" is a premise here that the spike tests rather than states.

**Beni runs the device lines.** Only his iPhone can. The results quote only sanitized measurement records from his log, excluding signing, provisioning and installation output and account identifiers, and Pass 1, Pass 2 and Pass 2.5 mark those numbers as Beni's run rather than as re-run.

## Decision rule

Registered here before any spike code exists. The spike branch is cut from a `main` that holds this file with Beni's thresholds in it.

**Choose Path A if all of these hold** for one bundle variant:

1. **Q2:** parity is 100% on every fixture, in both engines, in both locales and on the iPhone, against the merged core with nothing edited.
2. **Q3:** both medians on the device are under the thresholds below.
3. **Q5:** no App Review blocker to executing bundled JavaScript.

**Choose Path B only if A fails one of those.** A median inside its close-call band is reported as a close call beside the path the clauses name, and the band does not replace that path. If either gated median is inside its band, the whole result is a close call. Beni rules, and preference does not resolve it.

Pre-registered edge cases:

- If only `standalone` passes, the unedited core has not met the rule at that SHA. The results report Path A as conditional on that core change landing through the normal workflow, and Beni rules on it as a close call. It does not select Path B.
- A host shim may define host globals the bundle calls, such as `console`, and nothing else. A shim that changes a result is a core change. So is any other change needed in core. Clause 1 then fails at that SHA, and the results say what would fix it, so Beni can weigh it as a close call.
- A second locale that cannot be run in an engine fails clause 1, as under Q2.
- A divergence on a reported edge case, and a worst run, are reported and do not gate.
- The two medians gate separately, and no joint per-launch gate applies. The paired measurements are reported, so Beni can see a result where the medians pass and few launches meet both limits.
- A harness that cannot fail, or a skipped comparison, is not a pass. Q1 failing means Q2 cannot pass.
- The path-neutral items under Q5 do not count for either path.
- Q4's size informs Beni's reading of a close call. It does not override a clear result either way.
- Beni rules on the results, and ADR-0009 moves from Proposed then.

**What a pass does not prove.** It measures the terms loader. The engine, schedule, alert rules and CSV parsing do not exist yet, so a pass says this path works for the core as it stands at the spike's base. It does not say the load time will hold as the core grows, and ADR-0009's "Revisit when" covers that.

**Thresholds, set by Beni on 2026-11-02:**

| Measure, on Beni's iPhone, Release build | Proposed threshold | Close call if within |
| --- | --- | --- |
| Median over 5 fresh launches, to create a JSContext and evaluate the bundle | 500 ms | 400 to 600 ms |
| Median over the same 5 launches, of the first `loadTerms` on `example-autocall.yaml` | 50 ms | 40 to 60 ms |

Why these: the app runs the core off the main thread, at import and when opening, so the load is a delay a person may see and is not first-frame time. The only anchor so far is V8, not JavaScriptCore, on an Apple M4 with Node 24.22.2, labelled ESTIMATE as a guide to scale. Over three runs each, at a tree equal to `3bceb20`'s: importing the core entry takes 93 to 103 ms with the JIT and 129 to 131 ms with the JavaScript compiler flags under "Anchor", and `loadTerms` on `example-autocall.yaml` has a median of 0.94 to 1.05 ms with the JIT and 2.33 to 2.44 ms with those flags, with a worst of 8.3 to 10.4 ms and 9.3 to 9.6 ms. The script is under "Anchor".

## Mutation floor

The harness is the claim, so it must be shown able to fail. Listed in the PR body, with what caught each:

- altering one output byte;
- reordering two diagnostics in one output;
- changing one diagnostic's column;
- adding a `node:fs` import to the bundle's entry;
- adding `montecarlo` to the bundle;
- running both "locales" under one locale;
- running a variant on fewer than 31 fixtures;
- dropping the snapshot first line from a notification built by the harness.

The spike PR's claims list gives one command per row, and each of those commands exits nonzero. AC4 is the first row's. The others are names until that PR. Each command first proves the unmodified comparison passes, introduces only its named mutation, and checks for the intended mismatch or coverage failure. A missing tool, a setup error or an unrelated nonzero exit is not a killed mutant. After restoration, the comparison must pass again.

## Anchor

The script behind the ESTIMATE under "Decision rule". Run it from a clone with `pnpm install --frozen-lockfile` done, as `node anchor.mjs "$PWD"`, and as `node --no-opt --no-maglev --no-sparkplug anchor.mjs "$PWD"`. Those flags do not make the process interpreter-only: V8 can still compile regular expressions. They are an ESTIMATE of the effect of disabling those JavaScript compilers, not an iPhone no-JIT measurement. `--jitless` cannot be used, because Node's TypeScript stripping needs WebAssembly.

```js
import { readFileSync, readdirSync } from "node:fs";
import { join } from "node:path";
const root = process.argv[2];
const t0 = performance.now();
const core = await import(join(root, "packages/core/src/index.ts"));
const t1 = performance.now();
const dir = join(root, "fixtures/synthetic/terms/valid");
const big = readFileSync(join(dir, "example-autocall.yaml"), "utf8");
const s = [];
for (let i = 0; i < 20; i += 1) {
  const a = performance.now();
  core.loadTerms(big, "b.yaml");
  s.push(performance.now() - a);
}
s.sort((a, b) => a - b);
console.log(JSON.stringify({ importMs: t1 - t0, medianMs: s[10], worstMs: s[19] }));
```
