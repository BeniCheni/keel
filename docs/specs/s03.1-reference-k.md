## Goal

Pass M checks the engine against a reference that Codex wrote from the S03 spec. On the 11 golden cases the two agree. PR #38's Pass 2.5 found an input shape outside those cases where they differ (`docs/reviews/pr-38-pass-2.5.md`, finding 1). The shape is a listed schedule, a known final valuation date and no item dated on it. There, the reference counts an item dated after that date toward `k`, and the engine does not. Both return `unavailable` with no payout; only the reference's list of reasons differs. Beni ruled that the engine stands.

S03.1 changes the reference to match. It also adds two golden cases. With them, Pass M itself would catch this disagreement, or the year-10000 one that ruling C settled, if either came back.

## Decisions

Each of these is open to the plan challenge, except where a ruling of Beni's settles it.

1. **The engine stands (Beni's ruling of 2026-11-13, "No (Recommended)").** He gave it to "Does a listed item dated after the final valuation date count toward k?". S03's Events states the rule, as amended in this spec PR. No file under `packages/plugin-mln/` changes except test files.
2. **The reference follows S03's Events.** Codex amends `observation_events` in `tools/reference/payoff.py`. With a listed schedule, a known final valuation date and no item dated on it, an item whose known date is after that date is not an event and is not counted in `k`. Nothing else in the reference changes, unless a new golden case shows another disagreement. The PR body then names, for each change, the S03 rule it follows. If S03 does not settle the case, the builder stops and reports.
3. **Two golden cases let Pass M see both disagreements found off the golden set in PR #38.** Pass M stays a review step, as S03 Decision 12 sets, and `pnpm verify` runs no Python. The cases are defined under Frozen values.
   - `g12-listed-after-final` has the `k` shape.
   - `g13-year-10000-slot` is ruling C's case, in which the final valuation date's nearest slot falls in year 10000.

   The registered generator writes both, like the other cases. The 11 existing cases stay byte-identical, and the generator's version moves from 1 to 2.
4. **The generator gets the two guards PR #38's Pass 2.5 found missing.**
   - Finding 3, Medium: a committed test fails when `pushClose` stops refusing a rejected fixed close.
   - Finding 4, Low: the generator writes no close for a row's worst member, silently, when the row has `worstTicker` and `seedBelow: true` but no `missing`. It must instead stop with an error naming the case.
5. **The new cases' independence comes from where S03's does.** Their expected outputs come from the engine (S03 Decision 12). They are kept honest by the values frozen here, which a test asserts, and by Pass M. Codex read the engine at PR #38's Pass 2, so this reference change is written from S03's amended Events, not from a fresh reading. The PR body says which rule each reference change follows.

## Frozen values

Each has one close per member on `asOf`, drawn as the generator draws every case's `asOf` closes: a ratio from the member's own seeded stream, in steps of 0.0001 from 0.6000 to 1.3000 (`tools/generators/golden/generate.mjs:394-399` at `9ec6fd0`).

  - On this case, the reference at `origin/main` adds `{ "code": "final-valuation-off-cycle" }` after that reason.
- **`g13-year-10000-slot`.**
  - Terms: B with trade 9999-05-28, settlement 9999-06-01, first call observation 9999-12-01, final valuation date and maturity 9999-12-31, and `call.frequency` `monthly`, each `primary`. Its estimated schedule has one entry, 9999-12-01. `asOf` is 9999-11-30.
  - `evaluateNote` gives:
    - status `live`, no rows;
    - `next` of `{ "kind": "call", "scheduleIndex": 0, "date": "9999-12-01", "evidenced": true }`;
    - `payoutCents` null, `reasons` empty, and `unverified` `["dates.observation_schedule"]`.
  - `payoutSchedule` gives one call, with index 0, date 9999-12-01, `premiumMonths` 6 and `payoutCents` 104250. `final` is `{ "date": "9999-12-31", "evidenced": true, "premiumMonths": 7, "aboveCallCents": 104958, "atOrAboveBarrierCents": 100000 }`, and `unverified` is `["dates.observation_schedule"]`.
  - The reference as of `3e48b83` gives `unavailable` on both.
